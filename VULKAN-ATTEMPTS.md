# Attempts to produce a Vulkan-enabled llamafile

Goal: a single `.llamafile` for LFM3-1.7B QAD Q4_0 that uses a Vulkan-capable
GPU when present and falls back to CPU otherwise. **Not achieved.** This file
records every attempt, what we learned, and the working alternatives.

## Background: llamafile anatomy

A `.llamafile` is three things concatenated:

1. a small shell stub that launches it on Linux/macOS/Windows
2. a cosmopolitan binary (~47 MB): the llama.cpp engine compiled with `cosmocc`
3. a zip archive (~1 GB): the GGUF weights + assets (GPU DSO, licenses)

The engine reads the weights through Cosmopolitan's `/zip/` pseudo-filesystem
(mapped onto the executable itself). The GPU backend is a **DSO** (`ggml-vulkan.so`)
that the engine dlopen()s at runtime, extracted from the zip.

Mozilla builds the engine **from a patched llama.cpp tree**: 49 patches adapt
llama.cpp to Cosmopolitan libc, three of them specifically rewrite the Vulkan
backend (`ggml-vulkan.cpp`, `ggml-vulkan-buffers.cpp`, `ggml-vulkan-common.h`).
Those patches and the engine must come from the **same tree**, or the ABI does
not match.

## Attempt 1 — compile vulkan.sh against the pinned llama.cpp (unpatched)

- tree: llama.cpp @ `8642541b` (the llamafile v0.10.7 pin), **no patches**
- DSO built and loaded into the engine on u24-desktop (no GPU: "No devices
  found", fallback to CPU — correct)
- transferred to **u24-server** (RTX 4060 Ti 16 GB, driver 580.178.04,
  ICD `nvidia_icd.json` present)

**Result:** the engine loaded the DSO, enumerated the device
(`NVIDIA GeForce RTX 4060 Ti, KHR_coopmat`), assigned **all 25 layers to
Vulkan0**, then **segfaulted** while creating tensors (blk.4).

**Why:** the unpatched DSO uses structures that differ from the patched engine.
109 lines of the `ggml-vulkan.cpp` patch change buffer creation and memory
alignment; without them the two components disagree.

## Attempt 2 — DSO from the patched tree, engine binary unpatched

Same crash class, different point (`GGML_ASSERT(buft) failed`): the DSO now
matched the patched code but the **engine** did not, so the mismatch persisted.

## Attempt 3 — DSO and engine from the same patched tree

- tree: llama.cpp @ `8642541b` **with all 49 llamafile patches applied**
- both `ggml-vulkan.so` and the engine binary built from this tree

**Result:** cannot ship as a single-file llamafile. The engine built from a
plain tree **requires `/zip/` support compiled into Cosmopolitan** to read its
own bundled weights; this build (cosmocc without the full APE toolchain state on
u24-server) either fails to open the GGUF entry
(`failed to open GGUF file: Not a directory`) or, with `-m` pointing inside,
fails at the same point. The Cosmopolitan build environment (`build/tags.mk`,
`build/deps.mk`, complete submodules) is generated by `make setup` from the
llamafile tree and was not reproducible from a partial checkout.

**Verdict:** matching DSO + engine requires building **everything** from the
llamafile tree with its own cosmocc toolchain (`make cosmocc` + `make vulkan` +
`make o//llamafile/llamafile`). This is a full llamafile build, ~30–60 minutes,
and was not completed in this session.

## Attempt 4 — forced `--gpu vulkan` on a host without Vulkan

The launcher fails fast with an explicit error (never silently falls back to
CPU): `--gpu vulkan was explicitly requested but Vulkan is not usable on this
system`. `--gpu auto` (the default, and what pi-embedded-ai uses) falls back to
CPU correctly.

## What works: GPU via CUDA llama.cpp (verified)

The GGUF (extractable from any `.llamafile` — it is a zip entry) served by the
official CUDA build of llama.cpp on u24-server (RTX 4060 Ti 16 GB):

| Metric | GPU (CUDA, `-ngl 99`, 32k ctx) | CPU (llamafile v0.10.7) |
|--------|-------------------------------|--------------------------|
| prefill | **9206 tok/s** | ~89 tok/s |
| generation | **172 tok/s** | ~9 tok/s |
| VRAM | 1650 MiB (32k ctx) | — (CPU: ~3 GB RAM) |

```sh
docker run --rm --gpus all -p 8080:8080 -v $PWD:/models \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/LFM3-QAD-Q4_0.gguf -ngl 99 -c 32768 --host 0.0.0.0 --port 8080
```

## Vulkan build recipe (for the future)

To retry the single-file GPU llamafile properly:

1. on the build host: clone the **full** mozilla-ai/llamafile tree
   (not shallow — `make setup` needs complete submodules)
2. `make setup` (submodules + applies all 49 patches to llama.cpp)
3. `make cosmocc` (builds the cosmopolitan toolchain)
4. `make vulkan -j$(nproc)` (builds `ggml-vulkan.so` from the **patched** tree)
5. `make -j$(nproc) o//llamafile/llamafile`
6. `python3` zip-append: `ggml-vulkan.so` + the GGUF, keeping the `.cosmo` stub
   as the **first** zip entry and preserving every other entry in order
7. test on a GPU host: `--verbose` must log
   `Vulkan backend registered with GGML` and layers assigned to `Vulkan0`,
   then `/health` returns 200

Estimated build time: ~30–60 min. Output is x86-64 glibc; the DSO is not
portable across ABIs (musl/macOS/ARM need their own builds).

## The pre-existing artifact

`models-v2` (`LFM3-vulkan.llamafile`) was our attempt at step 6 with a DSO from
attempt 1: it runs on CPU (the engine silently skips an incompatible DSO) but
cannot use the GPU. Kept published but marked experimental in `MODELS.md`.
